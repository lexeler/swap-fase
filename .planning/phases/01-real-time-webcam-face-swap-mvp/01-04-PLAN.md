<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user file → image decoder | The load-photo dialog accepts arbitrary user-chosen image files passed to `cv2.imread` + face detection. |
| UI thread ↔ inference/capture threads | Controls mutate shared `AppState`; all access must be lock-guarded. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-15 | Denial of Service | non-image / corrupt / no-face target photo crashes the app | mitigate | Load-photo handler checks `cv2.imread` for None and catches `NoFaceError` → friendly dialog, keeps the previous target, no stack trace (precursor to Plan 05 polish; SWAP-01 robustness). |
| T-01-16 | Tampering | data race on `target_face` during live change | mitigate | `AppState.set_target` replaces the cached embedding atomically under the lock; the inference loop reads it under the same lock — clean swap with the loop still running (UI-03, D-10). |
| T-01-17 | Denial of Service | Stop / device-switch leaking the camera handle | mitigate | Stop and device-switch call `.stop()` + join + `cap.release()`; `closeEvent` releases on exit (Pitfall 10) so re-open always works. |
| T-01-18 | Information Disclosure | persisting the user's target photo/path to disk | mitigate | No persistence by design (D-09) — the photo lives in memory only; acceptance asserts no disk writes of the path. |
</threat_model>
